# ADR 0031 — A job may pull data from the control host; detachment becomes conditional

## Status

Active. **Supersedes [ADR-0005](0005-agent-lifecycle.md)**, whose lifecycle decision
it carries over unchanged except for one point: detachment is no longer
unconditional. ADR-0005 states that any change to the lifecycle requires a
superseding ADR, which is why this record replaces it rather than amending it.

## Context

Three needs cannot be expressed under the current model, and they are one subject:

1. **Content computed mid-run.** Delivering a file whose content depends on something
   the run just produced. Shipping everything up front assumes everything is known up
   front, which stops being true as soon as a step produces data.
2. **A value crossing hosts.** Reading a secret generated by an install on `web` and
   injecting it into a config on `app`.
3. **A secret pulled on demand**, so it never leaves the control host unless a target
   actually needs it.

What the code does today, verified rather than recalled:

- `orchestrator.Run` iterates blocks **sequentially**, so `on web { … }` completes
  before `on app { … }` starts. A cross-host ordering dependency already works —
  **because the control host is present to sequence it**.
- Within a block, hosts run in parallel (`internal/fleet`).
- `proto.Request` carries `Mode`, `Defs`, `Steps` and **no variable table**: values are
  substituted per host before the request is built, so a target receives only what
  concerns it. This is what keeps a secret off machines that do not use it
  ([ADR-0018](0018-secrets.md), [ADR-0025](0025-secrets-at-rest-tmpfs.md)).

The decisive observation is that **the control host is already required for the whole
plan**. ADR-0005's detachment does not let an operator walk away from a multi-block
plan; it guarantees something narrower and still valuable — a *single job* survives an
SSH drop, and the control host reconnects to collect its result. Allowing a job to ask
the control host a question is therefore a change of degree, not of nature: it removes
that narrower guarantee, for the jobs that use it.

## Decision

### 1. A job may request data from the control host while it runs

The agent may issue a request over the existing SSH connection and block until the
control host answers. This covers content computed mid-run and secrets fetched on
demand: a value the plan could not know in advance is asked for at the moment it is
needed.

The channel carries **data only** — never a command to execute. The control host reads,
renders, and answers; it never runs a shell on the operator's machine. Shell execution
stays what shellf is for: commands on remote targets.

### 2. Detachment is conditional, not abandoned

A job that requests nothing from the control host stays **detached**: it survives an SSH
drop mid-job and the control host reconnects to collect, exactly as ADR-0005 grants.

A job that issues a request is, from that moment, dependent on the control host: if the
connection drops while it waits, the job fails rather than hanging. It must fail with a
message naming the pending request, so the cause is not mistaken for a target problem.

Detachment is therefore a property of a job, not of the agent. Plans that never touch
control-host data keep today's resilience with no change.

### 3. The control host serves only what the plan declared

Before sending, the control host derives from the plan the set of resources a job may
legitimately request. Any request outside that set is **refused**, with the requested
resource named in the error.

This is not defensive programming, it is the condition that makes the channel safe.
Instructions can come from third parties ([ADR-0016](0016-remote-modules.md)); without
this rule, an imported def could ask for `~/.ssh/id_ed25519` and the control host —
the machine holding every key and secret — would answer. A declared set also keeps the
existing property that a missing file is reported before the first connection rather
than mid-deploy.

### 4. Everything else in ADR-0005 is carried over unchanged

Binary cached on disk and reused; agent stays alive between jobs, watching a request
file (no listening socket); self-terminating after an inactivity TTL, erasing its
workdir and its own binary; nothing survives a reboot; `clean` forces the wipe early.
The model remains a **transient resident**.

## Rejected alternatives

- **Ship everything up front, no channel.** Simple and preserves detachment outright,
  but it cannot express content that does not exist yet when the request is built. It
  also forces every secret used anywhere in the plan to travel, which is what pulling
  on demand exists to avoid.
- **Drop detachment entirely.** Simpler to reason about — one rule instead of two — but
  it removes resilience from the majority of plans, which request nothing, to
  accommodate the minority that do.
- **Let the agent read the control host directly** (mounted share, reverse copy).
  Requires infrastructure on the operator's machine and inverts the trust direction
  permanently, where a declared, per-run set is bounded.
- **Serve any request the agent makes.** Rejected in §3: it hands arbitrary read access
  to the operator's machine to any imported def.
- **Run shell on the control host.** The channel would then execute code locally, and a
  third-party def could do anything on the operator's machine. Data only.

## Consequences

- The protocol gains a request/response channel; the agent gains a blocking wait with
  a failure path when the connection is gone.
- The control host computes, per run, the set of resources it will serve, and refuses
  the rest by name.
- Two classes of job now exist — detachable and control-dependent — and the report must
  make clear which a failure belongs to.
- `--check` must state what it does when a step would request data: whether the request
  is served (it is a read, so it can be) or reported as undetermined. Settled in the
  primitives ADR, which introduces the requests themselves.
- ADR-0005 keeps its body and is marked superseded by this record.

## Out of scope

- **A value captured on one host reaching another** (need 2 above). The channel lets a
  job *ask*; it does not decide whether a capture outlives its `on` block, what its
  scope is, or what `--check` reports for a step consuming a value no previous block
  produced. That is a separate decision, tracked on its own.
- The primitives that use the channel (`%file.read` and friends) and their syntax.
